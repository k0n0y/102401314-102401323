## 十、队友评价与个人总结

> 本节为结合项目记录代拟的个人表达，发表前由本人确认是否符合自己的理解和评价；不把辅助开发或自动检查写成本人独立编码、亲自操作的经历。

### 10.1 对曾炜毅的评价

从需求复审和主仓库的协作记录来看，曾炜毅值得学习的地方是持续追问交付结果是否真的符合要求。最初的离线版能够展示页面，但跨客户端共享仍然缺失；围绕这一点继续复审，促成了共享服务和联网 APK 的补充。手机连接失败后，又转向模拟器验证的可行路径。这种从使用结果检查功能的思路，有助于发现仅看界面时容易忽略的问题。

主仓库维护同样体现了对交付质量的关注。README 运行记录提交后，维护者核对了系统名称与版本的矛盾，补充修正并保留原提交完成合并。代码之外的使用说明也需要复审，这一点值得在后续合作中继续保持。

建议改进的是更早安排验收和个人记录。需求分析时就应明确使用哪些客户端、由谁完成哪一段操作、出现异常时怎样留存证据；每个阶段结束后及时记录个人投入和复核结果。这样可以减少后期集中整理材料的压力，也能使分工从任务安排落实为清楚的完成记录。

### 10.2 本人总结

从本次服务代码和测试材料来看，测试设计需要围绕真正影响结果的条件展开。更新状态的按钮是否可见，只是界面层面的检查；权限是否可靠，需要使用另一个发布者的凭证直接请求接口，并确认服务器拒绝后原记录仍然没有变化。这样的案例同时检查返回值和数据状态，比只判断接口是否报错更有解释力。

重复提交、并发发布和服务重启也让我更清楚地理解共享数据的风险。重试应返回已经保存的记录，两个客户端发布不能互相覆盖，服务重启后信息和凭证应仍然有效。相应的测试不仅要写正常输入，也要根据源码中的分支、唯一约束和时间判断构造反例，并使用临时数据库避免污染正式数据。

协作材料应当支持复现。当前 README 的 PR 包含运行环境、命令和结果，提供了一个可以核对的贡献范围。与此同时，健康检查通过只说明服务有响应，不能直接推出 App 的发布、搜索、联系和状态更新全部正常。整理报告时，测试输出、模拟器截图和成员亲自操作应分别说明，不能相互替代。

今后的改进重点是把测试与记录放到开发过程中：先写明输入、预期和设计依据，运行后留下结果，发生错误时记录尝试与修正，再提交能够说明问题的改动。个人耗时和操作经历也应同步记录。辅助工具可以提高实施效率，但最终仍要能够解释测试为什么覆盖了相应风险，以及哪些环境还没有得到验证。
