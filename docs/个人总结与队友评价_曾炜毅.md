## 十、队友评价与个人总结

### 10.1 对陈勇昊的评价

从本次已经保留的协作记录来看，陈勇昊值得学习的地方是把运行方法和运行结果一起整理进交付文档。其 Cgg0024 账号通过 fork 提交了 README 运行记录，内容包括环境、测试命令、55 项测试输出和服务健康检查。这使其他人能够沿着明确的步骤尝试运行项目，也让测试结论有对应的记录可以查阅。对课程项目而言，完成程序之后继续补充可复现的说明，是很有价值的工作习惯。

建议改进的是环境信息的复核方式。原 PR 中的 Windows 名称与版本、构建号不一致，后来由维护者修正。下次可以在提交前逐项核对系统版本、运行命令和截图来源；健康接口检查与 App 完整流程也应分别记录。这样可以减少复审返工，让说明中的每个结论都与证据对应。

### 10.2 本人总结

这次项目最值得总结的是对“实现完成”的理解。原型中能够看到公共列表，并不意味着不同安装实例真的共享数据；只有甲发布的信息能被乙读取，甲更新状态后乙也能看到结果，才形成了作业要求的使用闭环。从离线版补充为共享版的过程说明，复审需求时需要同时检查页面、数据来源和状态传播。

用户侧的运行过程也是产品的一部分。服务已经启动，手机仍可能无法连接；使用模拟器时又需要明确服务地址与 ADB 转发。README 如果只写“安装后使用”，其他人就很难复现。今后整理交付材料时，应把安装、启动、连接、发布、搜索和更新状态组织成一条可以照着操作的路径，并说明常见失败时应该检查什么。

仓库维护方面，本次保留了队友的原始提交、维护者的修正和合并记录。文档问题可以通过一个清楚的修正提交解决，保留原作者的贡献，也便于以后追踪改动原因。对辅助生成的代码，仍需要能够解释功能、权限和异常处理；程序通过自动检查不能替代本人理解和复核。

当前过程记录的不足是个人投入没有形成连续计时记录，本次 PSP 采用审核确认的回顾估计。下一次应从开始就分别记录 PSP，完成一个模块后及时写明修改范围、测试结果和问题，而不是到报告阶段再回忆。验收时也应把设备环境、操作步骤与结果一起保存，使报告内容便于核对。
